# 1G workflow engine: implementation decisions

Status: **confirmed. 1G-a is written; 1F and 1G-b are pending.** Decisions 29 to 33 were added while implementing. It covers the `sales` and `tasks` modules. Business rules are not repeated here: they live in the State Machines & Permissions Spec (sections 2 to 5), the Data Model and the Architecture & API document. This file records only the choices those documents leave open.

## Order of work

| #   | Decision                                                                                                                                                                                                                                                                                                                | Why                                                                                                                                                                                                                          |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | 1G is built in two slices with 1F in between: **1G-a** (sales and the task engine, including the per-task completion rules, without the real document check), then **1F** (documents), then **1G-b** (the real document check wired in, edit of completed tasks with the financial lock, permanent delete).             | `documents` has a foreign key to `task_instances` and every upload route is nested under a task, so 1F cannot be built or tested without sales. Completing a task needs the documents check, so 1G cannot finish without 1F. |
| 2   | `tasks` asks one question of `documents` through a small interface: `MissingSlots(tx, taskInstanceID, requiredSlots)`. `tasks` decides which slots are required (it knows the customer type snapshot, so the conditional Task 2 _Vigencia de Poder_ rule stays with it).                                                | Keeps the dependency direction from the architecture table (`tasks` depends on `documents`) and keeps the rule next to the task that owns it.                                                                                |
| 3   | Until 1F existed, the interface had a stub that reported nothing missing, wired **only** when `APP_ENV` was `local` or `test`, and `complete` answered `DOCUMENTS_UNAVAILABLE` (503) elsewhere. _(As built: the stub is retired; the documents service from 1F answers the question, see `1f-documents-decisions.md`.)_ | Same pattern as the storage adapter in 1E (decision 11): a missing dependency must never look like success, and a deployed build can never complete a task without its documents.                                            |

## Structure and transactions

| #   | Decision                                                                                                                                                                                                                                                     | Why                                                                                                                                                                                                            |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 4   | `sales` owns `sale_registers`; `tasks` owns `task_instances` and the five detail tables. `sales.Create` calls `tasks.CreateForSale(tx, ...)` inside its own transaction.                                                                                     | Matches the module table. One transaction is required anyway: the commit-time trigger (EF003) rejects a sale without 13 tasks and its three one-to-one rows.                                                   |
| 5   | A new sale inserts the sale, 13 `pending` tasks, and empty `sale_financials`, `sale_due_diligence` and `sale_fulfillment` rows. `sale_payments` and `sale_invoices` rows are created on the first save of Tasks 4, 5 and 6 (upsert).                         | The trigger only requires the first three. Payments and invoices are "at most one per kind", so creating them on demand avoids empty rows and keeps the unique constraints meaningful.                         |
| 6   | Series, VIN (Task 3) and license plate (Task 10) are columns of `sale_registers`, but the Task 3 and Task 10 forms edit them. `tasks` writes them through a narrow `IdentifierWriter` interface that `sales` implements and `main.go` injects.               | `sales` depends on `tasks`, so `tasks` importing `sales` would be a cycle. The interface keeps table ownership intact without one.                                                                             |
| 7   | Every use case locks the sale first (`SELECT ... FOR UPDATE`), then its task rows, in that order, in one transaction. Audit rows are written in the same transaction.                                                                                        | Architecture section 7. A fixed lock order prevents deadlocks between two simultaneous transitions on the same sale.                                                                                           |
| 8   | Transition routes (start, complete, restart, reopen) carry no version: the action in the path implies the required status, and a repeat finds the status changed and answers `TASK_INVALID_STATE` (409). Data saves carry the **task instance's** `version`. | No idempotency keys are needed (architecture section 7). One version per task is simpler for the client than one per detail table, and Tasks 1 and 3 write disjoint columns of the same `sale_financials` row. |
| 9   | Milestones and the current task come from `v_sale_milestones` and `v_sale_current_task`. Go never re-derives them.                                                                                                                                           | One shared derivation serves the portal, filters and BI (spec section 4).                                                                                                                                      |

## Sales

| #   | Decision                                                                                                                                                                                                                                                                                                                                      | Why                                                                                                                                   |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| 10  | Creating a sale: an Advisor may omit `assignedAdvisorId` or send their own id (any other id is 403). Manager and Admin must send an **active** Advisor. Inactive customers answer `CUSTOMER_INACTIVE` (422); a model, version or color that is not selectable answers `VEHICLE_NOT_SELECTABLE` (422).                                         | S1 in the spec. Closes the open item left in the 1E customers document. An explicit 403 is clearer than silently ignoring a wrong id. |
| 11  | The sale snapshots (customer name, document, type, vehicle names, reference price) are read inside the creation transaction, with the customer and version rows locked `FOR SHARE`.                                                                                                                                                           | A catalog price edit or a customer deactivation committing mid-request cannot produce a snapshot that disagrees with the checks.      |
| 12  | Advisor scope is one SQL rule: `assigned_advisor_id = actor`. A sale outside scope answers 404 for every route, and list totals are counted inside the scope.                                                                                                                                                                                 | FR-013 and FR-039. Reassignment takes effect with the commit because nothing is cached.                                               |
| 13  | `GET /sales` supports `q`, filters (state, current task, milestone, advisor, customer type, temperature, model, version), a whitelist of sort fields and the standard paging (20 per page, at most 100). `q` searches customer name, series, VIN and plate with the existing trigram indexes, and the customer document by prefix.            | FR-039. Anything outside the whitelist is a 400, so no user text reaches `ORDER BY`.                                                  |
| 14  | Cancel authorization uses the current task number `c`; the number is stored in `cancelled_at_task_number`. Reopen uses the stored number: `c` 1 to 6 allows Manager or Admin, `c` 7 or more allows Admin only. Cancelling needs a category and, for `other`, a text.                                                                          | Spec section 3. Storing `c` means the reopen rule does not have to be rebuilt from history.                                           |
| 15  | Reopening a cancelled sale checks series, VIN and plate through the partial unique indexes. A unique violation maps to `SERIES_ALREADY_USED`, `VIN_ALREADY_USED` or `PLATE_ALREADY_USED` (409) by index name. In the same transaction, the in-progress task's `due_date` moves forward by the time spent cancelled and its counters are kept. | Spec section 5.4. The shift is a data change at reopen time, so it cannot wait for the scheduler in Phase 3.                          |
| 16  | Reassignment requires an `active` sale and an active Advisor different from the current one (`SAME_ADVISOR`, 422). It writes `REASSIGNED` to the audit log.                                                                                                                                                                                   | S6. Reassigning to the same person would otherwise create a meaningless event (and a notification in Phase 2).                        |
| 17  | `PATCH /sales/{id}` edits notes only. Everything else on the sale changes through its own route.                                                                                                                                                                                                                                              | Sale data is immutable after creation except notes and advisor (spec section 3). The immutability trigger is the backstop.            |

## Tasks

| #   | Decision                                                                                                                                                                                                                                                                                                                    | Why                                                                                                                                                                    |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 18  | Data saves are drafts: fields may be empty. A save rejects impossible values (bad dates, formats, non-positive amounts) as field errors and returns out-of-order dates as `warnings`. Completeness and cross-field rules are checked only on `complete`, which returns **all** failing fields at once (422), not the first. | A form that saves progress needs partial data. Reporting every problem in one answer saves the advisor several round trips.                                            |
| 19  | Saving is allowed only while the task is `in_progress`; a `pending` task that was restarted keeps its data read-only. A sale that is not `active` rejects every task mutation (`SALE_NOT_ACTIVE`).                                                                                                                          | T1 to T4 and S4 in the spec: restart keeps data read-only, and a cancelled sale is frozen.                                                                             |
| 20  | Identifiers are normalized before validation: series and transaction or DAM numbers trimmed, upper-cased and stripped of spaces; VIN and plate upper-cased. The Spanish message states the format that was expected.                                                                                                        | The database CHECKs require normalized values, so normalizing first means a valid entry never fails at the constraint and the user never sees a generic error.         |
| 21  | Expected amounts (Task 4, Task 5 and the four Task 6 invoices) are computed by the server and never accepted from the client. They are refreshed on every save of that task **and again at completion, under the lock**, so the stored `expected_amount` is exactly what the completion check compared.                     | Task 1 or Task 3 amounts can still change while Task 4 is in progress. A stale stored value would make the mismatch CHECK describe a comparison that never happened.   |
| 22  | `completion_phase` is a pure function in `tasks/sla.go` that takes `started_at`, `completed_at`, the duration and the reminder interval from `task_definitions` (hours). It is table-tested at every boundary (79.9%, 80%, 100%, one interval, none). Phase 3A reuses it.                                                   | The database requires a phase on every completed task, so 1G needs it even though the SLA engine is Phase 3. One implementation avoids two definitions drifting apart. |
| 23  | `due_date` is `started_at` plus the duration in elapsed hours, computed in Go. Weekends and holidays never pause the clock.                                                                                                                                                                                                 | Spec section 5.1. Hour arithmetic in Go avoids any time zone surprises from interval math in SQL.                                                                      |
| 24  | Restart, reopen and edit of a completed task require a reason (trimmed, non-empty, at most 500 characters), stored in `audit_logs.reason`. Reopen writes `REOPENED`, restart `RESTARTED`, and an edit of a completed task `CORRECTED` (that edit ships in 1G-b).                                                            | The audit table already enforces a reason for these actions; the API rejects a missing one first with a field error instead of a database error.                       |
| 25  | The audit summary stores field names with before and after values for business data (amounts, dates, identifiers). Personal data (signer name and document number) records only "changed".                                                                                                                                  | Same rule as 1E customers decision 4: the audit trail must not become a second copy of personal data.                                                                  |
| 26  | **(1G-b)** The financial lock (Task 1 and Task 3 source amounts once any later task is completed; Task 4 and 5 deposited amounts once Task 6 is completed) is checked in the service, with the field-level error `LOCKED`. No trigger is added.                                                                             | The spec defines the rule in terms of task states the service already holds under the lock. The error can name the exact field and what to roll back.                  |

## Notifications

| #   | Decision                                                                                                                                                                                                                                                                                             | Why                                                                                                                                                                                                               |
| --- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 27  | 1G calls a `Notifier` interface at each trigger point (sale created, milestone tasks completed, advisor assigned, unassigned or changed), with a **no-op** implementation. It writes no `notification_logs` rows. The real outbox writer arrives with 2D, using the dedupe keys from the Data Model. | Rows written now would stay `pending` and be sent as a burst of stale emails to real customers the first time 2D runs. The trigger points are known now, so wiring them later is a one-line change per call site. |

## Testing

| #   | Decision                                                                                                                                                                                                                                                                                                                                                                    | Why                                                                                                                                      |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| 28  | Four kinds of test on top of the usual unit tests: authorization cases generated from the permission matrix (one per role and action), a randomized sequence test that applies valid and invalid transitions and checks the prefix invariant after each, two-goroutine tests for a double complete and a cancel racing a reassign, and the boundary table from decision 22. | The matrix and the invariant are the two things the spec says must never be wrong, and they are exactly what hand-written examples miss. |

## Added during implementation

| #   | Decision                                                                                                                                                                                                                                     | Why                                                                                                                                                                               |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 29  | Taking the snapshots of a new sale reads the `customers`, `vehicle_*` tables and the selectable views directly, with `FOR SHARE` locks, inside the creation transaction. It is the one place where one module reads another module's tables. | Decision 11 needs the rows locked in the same transaction as the insert, which a service method on another module's pool could not do without exposing transactional methods.     |
| 30  | A task's notes have no version: the last save wins and a notes save does not change the task `version`. An Advisor can write notes only while the task is in progress; Manager and Admin at any time while the sale is active.               | Notes are free text. Bumping the version would make a form someone is filling in stale every time a colleague adds a note.                                                        |
| 31  | The signer's document type and number are saved as a pair. Sending one without the other is `DOCUMENT_PAIR_REQUIRED`.                                                                                                                        | The table requires both or neither, and a field error is clearer than a constraint violation.                                                                                     |
| 32  | A payment or invoice whose amount differs from the expected one must carry its `mismatchReason` **in the same save**. If the amounts match again, a stale reason is dropped.                                                                 | The table has a CHECK that forbids storing a mismatch without a reason, so the rule is enforced at save time with a field error instead of at completion.                         |
| 33  | A date earlier than the day before the sale was created is a warning (`DATE_BEFORE_SALE`); Task 13 delivery before the Surquillo transfer is a warning (`DATE_OUT_OF_ORDER`). Years outside 2000 to 2100 and impossible dates are errors.    | The spec asks for out-of-order dates to warn and impossible ones to block. These are the only two orderings the documents define; others can be added without changing the shape. |

## Open items

- Please confirm decision 27. The alternative is writing `pending` outbox rows now and having 2D send only rows newer than its own release; I preferred the no-op because it needs no cut-off rule.
- Permanent delete of a sale (S7, Admin) moves to 1G-b because it needs `documents` to list the files for `storage_deletions` (reason `sale_deleted`). Two points to confirm: "Task 13 never completed" should also look at the audit log, since a reopened Task 13 has no `completed_at`; and the typed confirmation should be the customer's document number, because the sale has no short code.
- Who can read `GET /sales/{id}/history` is "per visibility" in the architecture table and is not defined elsewhere. Proposal: the same scope as the sale itself, with reasons shown to every staff role that can see the sale.
- The per-task payload schemas (13 of them) are written when 1G-a starts, from the master prompt, and added to `openapi.yaml`. The existing parity test will fail until each route is described.
- The customer portal's visibility rules (completed tasks only, hidden again on reopen) belong to Phase 2B. 1G only guarantees that reopen and restart clear the data a view would depend on.
- After 1G-a, `SalesWorkspace` can switch from demo data to the real API, as was done for customers and catalog. `roadmap.md` should then show 1H as "customers, catalog and staff done; sales and tasks pending".
- 1G-a was written without a Go toolchain available, so it has not been compiled or run. Run `make fmt vet test` first; the unit tests cover the validation, SLA and permission rules, and the database-backed flow tests are still to be added.
