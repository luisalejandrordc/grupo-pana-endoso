# 1G sales and task engine: implementation decisions

Status: the sale lifecycle and the 13-task engine are implemented and tested on the backend (`internal/sales`, `internal/tasks`, `internal/outbox`). The frontend for sales (1H) is next. File uploads belong to 1F, so tasks that require documents cannot be completed through the interface yet (see the first open item).

## What was built

- **Sales:** create (the customer and vehicle are recorded as snapshots), list/search/filter, detail with derived milestones, notes, reassign, cancel, reopen, permanent delete of test sales, and the sale timeline from the audit trail.
- **Tasks:** list and detail with calculated values, documents, warnings and the actions each person can take; start, complete, restart, reopen, save fields (draft while in progress, correction when completed), and notes.
- **Rules from the specification:** strict sequence with one task in progress; the cancellation and reopen matrix by role and stage; Advisors see only their own sales everywhere; SLA clocks and completion phases; financial field locks; unique series, VIN, plate, DAM, invoice and transaction numbers among active and completed sales; the milestone e-mails queued once per task.

## Decisions

| #   | Decision                                                                                                                                                                                                                                                                                                                                           | Why                                                                                                                                                                              |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | Every change to a sale first locks the sale row (`FOR UPDATE`). Task edits also check the task's own version.                                                                                                                                                                                                                                      | One sale is changed by one request at a time, so a double click or two people never corrupt the sequence. The database still enforces the shape at commit.                       |
| 2   | A sale gets a sequential number (new migration `0013_sale_numbers.sql`) and a code like `EF-2026-00419` (year of creation in Lima, number never reused).                                                                                                                                                                                           | People need to say which sale they mean, and the permanent deletion needs something to type. The specification had no sale number.                                               |
| 3   | A sale an Advisor does not own answers 404 `SALE_NOT_FOUND`, never 403.                                                                                                                                                                                                                                                                            | A 403 would confirm that the sale exists.                                                                                                                                        |
| 4   | Saving fields is a draft while the task is in progress: absent fields are left alone, an empty string clears a field, nothing is required until completion. A pending task is read-only; a completed task can only be corrected by a Manager or Admin with a reason, and the correction must leave it complete.                                    | FR-050 to FR-052. People enter data over days, but a corrected task must never become incomplete.                                                                                |
| 5   | Completion reports every problem at once (`TASK_INCOMPLETE` with the field list), including missing required documents as `documents.<slot>`. An amount that differs from the expected one needs a reason.                                                                                                                                         | The person fixes everything in one pass.                                                                                                                                         |
| 6   | The expected amount is stored only when a task is completed, and cleared when it is reopened.                                                                                                                                                                                                                                                      | The database refuses a differing amount without a reason while an expected amount is stored, and drafts must be savable.                                                         |
| 7   | Financial locks: task 1's amounts once any later task is completed; task 3's final Toyota amount once any task after 3 is; the deposits of tasks 4 and 5 once task 6 is.                                                                                                                                                                           | The specification's rule for amounts that later tasks depend on.                                                                                                                 |
| 8   | Impossible dates are refused (not a real date, before the year 2000, more than a year ahead). Out-of-order dates and dates after today only warn and never block. "Out of order" means earlier than a date from an earlier step: sale created, Pana payment, Toyota payment, invoices, registration, PDS transfer, equipment, Surquillo, delivery. | The specification says impossible values block and out-of-order dates warn, without defining the order. This is my reading; it is one table in `domain.go` if it needs changing. |
| 9   | Task 3's final Toyota amount is refused if it leaves a final commission that is not positive (initial Toyota plus initial commission minus final Toyota).                                                                                                                                                                                          | The database would refuse it with a generic error; this gives a message on the right field.                                                                                      |
| 10  | Reopening a cancelled sale shifts the running task's start time and due date forward by the time spent cancelled, so it resumes with the time it had left. If another sale took its series, VIN or plate meanwhile, the reopen is refused with that conflict.                                                                                      | Specification S5.                                                                                                                                                                |
| 11  | Cancelling needs both a category and a text. The running task stays in progress, frozen.                                                                                                                                                                                                                                                           | FR-043.                                                                                                                                                                          |
| 12  | Deleting a sale needs Admin, a reason, the typed sale code, and the sale must never have reached task 13 (checked in the audit trail, so a reopened delivery still counts). Its files are queued for deletion and removed after the commit; the audit rows survive.                                                                                | Specification S7.                                                                                                                                                                |
| 13  | Notifications are written to `notification_logs` in the same transaction as the change, with a dedupe key. A milestone task notifies the customer once, however many times it is reopened and completed; every reassignment gets a fresh key. Nothing is sent yet: the dispatcher is a later sub-phase.                                            | A notification exists if and only if the change committed.                                                                                                                       |
| 14  | The task detail returns `permissions` (what this person can do now) and `calculated` values.                                                                                                                                                                                                                                                       | The interface never has to re-derive the rules. The server still checks every request.                                                                                           |
| 15  | Task data for each task is a typed object; unknown fields are refused. Money is a decimal string, dates are `YYYY-MM-DD`.                                                                                                                                                                                                                          | A typo in a field name must fail, not silently save nothing.                                                                                                                     |

## Found by testing

- Notification keys built from a timestamp collide when two changes share an instant; they now use a random id.
- Searching a sale by its full code (with the year) matched nothing until the search was fixed to include it.
- Sorting descending by date left ties in ascending id order; ties now follow the sort direction.

## Open items

- **Documents (1F) block task completion in practice.** The engine checks required documents against the `documents` table, as the specification says, but nothing can upload a file yet. Until 1F, every task with a required document can be filled and validated but not completed through the API; the tests insert document rows directly. If you want to use the interface end to end before 1F, 1F should come next, or a development-only switch could be added (not recommended: it weakens a real rule).
- Reminders and the SLA scan (the jobs of 1J) are not implemented. The data they need (due dates, reminder counters) is kept correctly, including resets on restart.
- The sale and task notifications are queued but never sent.
- The date-order table (decision 8) and the 80% "approaching" threshold come from my reading of the specification; confirm them with the business.
