# 1F documents: implementation decisions

Status: **written, not yet compiled or run by the author.** It covers the `documents` module and the signed-URL support in the storage adapters. Business rules are in the Requirements Catalog (section 8, FR-065 to FR-072) and the Data Model; this file records only the choices those documents leave open.

| #   | Decision                                                                                                                                                                                                                                                                                                                                                                           | Why                                                                                                                                                                                              |
| --- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1   | Sale documents live in a **separate private bucket**, set with `R2_DOCUMENTS_BUCKET`. Configuration refuses the same name as `R2_BUCKET`, and a documents bucket without the rest of R2. Without it, documents use the local folder in local and test environments and an unconfigured store everywhere else (uploads and downloads answer `STORAGE_UNAVAILABLE`).                 | The catalog bucket must be publicly readable at `R2_PUBLIC_BASE_URL`. A document stored there would be readable by anyone who knows its address, which would defeat FR-070.                      |
| 2   | `storage.Store` gains `SignedURL(ctx, key, fileName, ttl)`. R2 builds a presigned GET (AWS Signature Version 4 in the query string) that sets `response-content-disposition` so the browser saves the file under its original name. Local and memory stores return a plain address.                                                                                                | R2 needs no SDK in this project, and the signing code is tested against the example printed in the AWS documentation. The local folder has no signing, which is acceptable for development only. |
| 3   | A download address lasts 5 minutes (`DefaultDownloadTTL`) and is issued only after role and scope are checked. A document of a sale outside an Advisor's scope answers `DOCUMENT_NOT_FOUND`, the same as a missing one. Each issue is logged with the document, sale and actor.                                                                                                    | FR-070. The address is the only way to reach a file, so a short life limits what a leaked address can do, and a 404 never reveals that another advisor's document exists.                        |
| 4   | The file is checked **by content**: a PDF starts with `%PDF-`; an `.xlsx` is a zip that has `[Content_Types].xml` and `xl/workbook.xml`; an `.xls` has the OLE header and a `Workbook` or `Book` stream name. The detected type must match the slot's `allowed_format`, and the stored `mime_type` is the detected one, never the browser's.                                       | FR-065: a renamed executable or a Word file must be refused. The three accepted MIME types match the table's CHECK.                                                                              |
| 5   | The original file name is kept as metadata only: reduced to its base name, stripped of control characters and cut at 150 characters. The storage key is `documents/<saleId>/<documentId>.<ext>` and never contains the name.                                                                                                                                                       | A name typed by a user can contain path tricks or characters a storage key should not carry. Keeping it out of the key also makes replacement safe: the new file always has a new key.           |
| 6   | An upload follows this order: check permissions without a lock (so a forbidden 10 MB upload is refused early), write the new object to storage, then record it in one transaction that checks again under lock. If the transaction fails, the new object is queued in `storage_deletions` and deleted. A replaced file is queued in the same transaction and deleted after commit. | Storage and the database cannot share a transaction. Writing first means a crash can leave an orphan object (which the queue removes) but never a row that points at nothing.                    |
| 7   | Who may change files: while the task is in progress, the assigned Advisor, a Manager or an Admin. On a **completed** task only a Manager or Admin may **replace** a file, with a required reason; nothing can be uploaded to a pending task, and removal is allowed only while the task is in progress. The sale must be active in every case.                                     | FR-050, FR-065, FR-068 and FR-069. Putting the replacement of a completed task's file here (and not in 1G-b) keeps all document rules in one module; the 1G-b edit of task data is separate.     |
| 8   | The uploader's reason is a text part of the multipart request. A replacement writes `REPLACED` with the old file's name, size and checksum next to the new ones; an upload writes `UPLOADED`; a removal writes `REMOVED`. No file content or storage key is ever audited.                                                                                                          | FR-068, FR-069 and FR-073.                                                                                                                                                                       |
| 9   | The task engine's question is answered by `documents.Service.MissingSlots`. The temporary stub of 1G-a is no longer wired anywhere; `tasks.StubDocuments` stays only for tests. `tasks.RequiredSlots` is exported and is the single definition of which slots a task needs, also used by the slot list.                                                                            | One definition of "required" cannot drift between the list a person sees and the check that blocks completion.                                                                                   |
| 10  | The slot list returns every slot, including empty ones, with `required` for the sale's customer type and `customerVisible` from the slot. Visibility is not stored per file.                                                                                                                                                                                                       | FR-067: the visibility of a slot is fixed. The customer portal (Phase 2) will read the same flag.                                                                                                |

## Open items

- `storagecleanup.RetryOpen` is still not scheduled; it belongs to the jobs sub-phase (1J), as decided in 1E. Until then a deletion that fails stays queued and is only retried when the same process handles another change.
- A download address is issued without checking that the object still exists in storage. A missing object shows up as an error from storage when the link is opened. Adding a cheap existence check (a `HEAD` request) is possible if FR-070's "clear error and logged" has to apply at issue time.
- The local folder serves documents publicly under `/media`. This is for development only and is logged as a warning at startup.
- Permanent deletion of a sale (S7, in 1G-b) has to queue every document key of the sale in `storage_deletions` with reason `sale_deleted` before the cascade removes the rows.
- The frontend upload and download controls are not part of this change.
