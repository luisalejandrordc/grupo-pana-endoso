# Sales frontend (1H, sales and tasks): implementation decisions

Status: **written, not yet type-checked or run by the author** (no Node dependencies were available where it was written). Run `npm run typecheck && npm test` first. It connects the employee frontend to the sales, tasks and documents API of 1G and 1F.

| #   | Decision                                                                                                                                                                                                                                                                                            | Why                                                                                                                                              |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1   | The real screens live in `features/sales/live/` and are chosen by `demoMode`, the same split customers and catalog use. The demo screens and their tests are untouched.                                                                                                                             | Demo mode keeps working for presentations, and the live code can be removed from or added to without touching it.                                |
| 2   | A sale has no short code in the API, so the screens show `Venta` plus the first eight characters of its id, in capitals.                                                                                                                                                                            | Same approach as customers (`ID · XXXX`). The customer name is what people recognize.                                                            |
| 3   | The task form draws itself from one table (`taskForms.ts`) with the API's own field keys. Only the fields that changed are sent, trimmed; an emptied field is sent as `null`; calculated fields are never sent. The server stays the authority: the client only decides what to show.               | One place describes 13 tasks, and a save never overwrites a value the user did not touch.                                                        |
| 4   | "Completar tarea" first saves any unsaved changes and then completes. A refused request keeps the screen as it was and shows the server's message, with each field error next to its field (`documents.<slot>` errors next to the document).                                                        | The server reports every failing field at once, so the person fixes them in one pass.                                                            |
| 5   | The financial lock table is repeated in the client (`lockedKeys`) only to disable those fields on a completed task and explain why. The server still refuses a locked edit.                                                                                                                         | A disabled field with a reason is clearer than an error after typing. The client copy cannot grant anything the server refuses.                  |
| 6   | Role rules (who can start, cancel, reopen, reassign, delete) are mirrored in `permissions.ts` to show or hide buttons. The server decides.                                                                                                                                                          | Buttons that always fail would be noise, but hiding them is a convenience, never the protection.                                                 |
| 7   | Every successful write invalidates every `["sales", ...]` query. The task form resets only when the task's version or status changes, so a file upload or a note does not wipe what was typed.                                                                                                      | One rule keeps the list, the detail, the tasks, the files and the history consistent without bookkeeping per screen.                             |
| 8   | The new-sale screen picks the vehicle from `GET /catalog/selectable` (what can be sold today) and the advisor from `GET /advisors`. A customer is found by name or document in the customers list, by an exact document lookup (which also finds customers of other advisors), or created in place. | The sale form can only offer what the server will accept, and an advisor can sell to a customer that belongs to a colleague, as the spec allows. |
| 9   | The hero shows the vehicle photo when the sale's color is still in the selectable catalog; otherwise a placeholder.                                                                                                                                                                                 | The sale stores names and the reference price, not an image. This is best effort until the API returns the image.                                |
| 10  | The history shows each event with a Spanish title, who did it and when, the reason, and one line per changed field (before and after). Personal fields appear only as "modificado". A task event is matched to its task through the task's id.                                                      | The server already keeps personal data out of the audit summary; the screen does not try to bring it back.                                       |
| 11  | `schema.d.ts` got the new schemas by hand, in the generator's style. Run `npm run api:types` to regenerate it from `openapi.yaml`; the result also adds the new paths and operations.                                                                                                               | The generator could not run where this was written. `npm run api:types:check` will pass again after regenerating.                                |

## Manual walkthrough

Sign in as an advisor with demo mode off, then:

1. **Nueva venta**: search or create a customer (a Diplomático avoids the power of attorney), pick model, version and color, priority, and register. The detail opens with 13 pending tasks and Task 1 ready.
2. **Task 1**: start it, enter 30000, 3000, 1000 and 1000 (the final price shows 35000.00), attach the PDF and the Excel quotation, complete.
3. **Task 2**: DNI 12345678, names, "No es PEP", régimen general, attach the identity scan and the affidavit.
4. **Task 3**: any series, a 17-character VIN without I, O or Q, final amount 30000 (the commission shows 3000.00), attach the settlement.
5. **Task 4**: BCP, today, an operation number, deposited 35000, attach the voucher. Try 34000 first: the form asks for the reason.
6. **Task 5**: BBVA, 30000, attach both files.
7. **Task 6**: four invoices (F001 to F004 series, any correlative) for 30000, 3000, 1000 and 1000, attach the four files.
8. **Tasks 7 to 13**: endorsed documents; DAM, aduana and canal; responsable; plate and registration date; transfer date; service order and completion date; delivery date and the signed record. The last completion closes the sale.

Then sign in as a manager to try the other paths: **Corregir datos** on a completed task (and the lock once the next task is completed), **Reabrir tarea**, **Reiniciar tarea**, **Reasignar asesor**, **Cancelar** and **Reabrir venta**; and as an admin, **Eliminar definitivamente** on a sale that never reached Task 13.
